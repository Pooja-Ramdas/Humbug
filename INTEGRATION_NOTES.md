# Integration Notes

## What Was Found in the Repo

### Web Framework
**None existed.** The repo contains four Python utility modules (`detection.py`,
`build_graph.py`, `generate_data.py`, and an empty `telemetry_sim.py`) but no
web server, no routes, no API layer. Everything had to be built.

### Existing Python Modules
| File | Role | Status |
|------|------|--------|
| `generate_data.py` | Generates synthetic pole/DT/feeder/substation data → SQLite + CSVs | Read-only — do not modify |
| `build_graph.py` | Builds a NetworkX `DiGraph` from the SQLite DB | Imported by backend as a library |
| `detection.py` | `compute_pole_statuses()` + `run_detection_pass()` | Imported by backend; minor additive changes only |
| `telemetry_sim.py` | Was **completely empty** | Written from scratch |

### Database Schema (data/data.db)
Generated by `generate_data.py --seed 42`:
- **2707 poles** across **40 DTs**, **8 feeders**, **4 substations**
- **24 of 40 DTs (60%) have no pole ordering** (seq_on_line / parent_pole_id = NULL)
- ~9% of poles have no device_id
- ~3% of poles have no pincode

Tables in the seed DB:
```
substations          (substation_id, lat, lon)
feeders              (feeder_id, substation_id, lat, lon)
transformer_registry (dt_id, feeder_id, lat, lon, capacity_kva, households_served)
pole_registry        (pole_id, lat, lon, feeder_id, dt_id, seq_on_line,
                      parent_pole_id, pole_type, ward, pincode, device_id)
ground_truth_topology  ← EVAL ONLY. Application code NEVER queries this.
meta                 (key, value)
```

Tables added by the backend at startup (not in seed DB):
```
telemetry       (id, pole_id, device_id, event, energized, ts, seq, battery_mv,
                  rssi, fw, received_at)
device_last_seen (device_id, ts, pole_id)
tickets         (id, scope, target_id, affected_pole_ids, status, confidence,
                  confidence_reason, lat, lon, pincode, feeder_id, created_at,
                  updated_at, acknowledged_at, crew_assigned_at, resolved_at,
                  verified_at, closed_at)
scheduled_outages (id, scope, target_id, start_ts, end_ts, reason)
```

## Endpoints Built

All endpoints are implemented in `backend/app.py` (FastAPI).

### Telemetry Ingest
| Method | Path | Purpose |
|--------|------|---------|
| `POST` | `/ingest` | Accept telemetry payload from pole devices. Handles at-least-once delivery (dedup by pole_id+seq), out-of-order messages, device_last_seen tracking. Triggers detection pass. |

### Network Data
| Method | Path | Purpose |
|--------|------|---------|
| `GET` | `/poles` | All poles: pole_id, lat, lon, dt_id, feeder_id, status (normal/fault/unknown/load_shedding), device_id, seq_on_line, parent_pole_id, ward, pincode, last_seen |
| `GET` | `/poles/{pole_id}` | Single pole detail |
| `GET` | `/network/edges` | All topology edges: {from, to, edge_type (span/membership/inferred), dt_id} |
| `GET` | `/transformers` | All DTs: dt_id, feeder_id, lat, lon, capacity_kva, households_served, topology_known |
| `GET` | `/feeders` | All feeders with substation linkage |
| `GET` | `/substations` | All substations |

### Tickets
| Method | Path | Purpose |
|--------|------|---------|
| `GET` | `/tickets` | List tickets; ?status=open filters to non-closed/non-verified |
| `GET` | `/tickets/{id}` | Full ticket detail |
| `POST` | `/tickets/{id}/acknowledge` | Transition detected→acknowledged |
| `POST` | `/tickets/{id}/assign-crew` | Transition acknowledged→crew_assigned |
| `POST` | `/tickets/{id}/resolve` | Transition crew_assigned→resolved (pending telemetry verification) |

**The UI cannot directly close or verify a ticket** — those transitions are
telemetry-driven only. The backend enforces this server-side; the UI reflects it
by disabling those actions.

### Simulator
| Method | Path | Purpose |
|--------|------|---------|
| `POST` | `/simulate/fault` | Inject a span/dt/feeder fault. Body: `{type, target_id}`. Generates realistic telemetry including ~30% message loss and fw-1.2 silent failures. |
| `POST` | `/simulate/restore` | Repair an injected fault. Body: `{type, target_id}`. Generates boot+power_restored telemetry for affected poles. |
| `POST` | `/simulate/noise` | Inject independent noise: `{noise_type: device_death|load_shed|duplicate_burst}` |
| `GET` | `/simulate/active` | List currently active injected faults (for the repair UI) |

### Scheduled Outages
| Method | Path | Purpose |
|--------|------|---------|
| `GET` | `/scheduled-outages` | List scheduled outages; ?from=&to= for range filter |
| `POST` | `/scheduled-outages` | Create a new scheduled outage (used by noise simulator) |

### System
| Method | Path | Purpose |
|--------|------|---------|
| `GET` | `/health` | Health check: `{status, pole_count, open_tickets, connected}` |
| `GET` | `/stats` | System stats for header widget |

## Live Updates Strategy

**Decision: Short-interval polling (3 seconds for pole status + tickets,
10 seconds for network edges/topology).**

Rationale: The backend exposes REST only. FastAPI SSE is technically possible
but adds connection management complexity and breaks behind many reverse proxies.
Since the brief's p95 detection-to-UI target is 120 seconds, 3-second polling
provides a 40× safety margin. This is noted honestly in the UI header as
"polling every 3s" rather than implying a push connection.

## Topology Inference (the 60% problem)

For DTs where `seq_on_line` / `parent_pole_id` is NULL:

**Approach: Geometric Euclidean MST from DT location.**
Build a minimum spanning tree over the pole coordinates, rooted at the DT's
lat/lon, using straight-line distance as the edge weight. This is a reasonable
proxy for the actual radial line layout because:
1. Real LT lines follow roads and right-of-way, which in a dense urban grid
   tend to minimize total wire length.
2. The `generate_data.py` correlated random-walk placement deliberately
   simulates road-following paths.

Known failure mode: MST inference will be wrong when two branches cross or run
parallel (e.g. a T-junction). Confidence decreases as branch count increases.
In the UI, **inferred edges are rendered as dashed dim lines** with a tooltip
"topology inferred (not surveyed)" — never silently presented as known topology.

For fault localization on topology-unknown DTs, the system falls back to
**DT-level grouping** (all dark poles under a DT → one ticket with
`scope=dt`). This is explicitly surfaced in the ticket UI as
"DT-level fault (topology unknown for this transformer)".

## Gaps / Open Items

### Deployment / Public URL
Not yet deployed. Options (in order of recommendation):
1. **Railway** — supports `docker-compose.yml` natively, free tier, cold starts
   in ~10s (note in README). `railway up` from the repo root is all that's
   needed.
2. **Render** — two services (backend web service + static frontend), free tier.
   Slightly more config (two `render.yaml` entries) but no cold-start issue on
   paid.
3. **Fly.io** — single-host, multi-process. Best latency, most config. Worth it
   if submission needs the performance SLA demonstrated live.

Recommendation: **Railway** for the submission (simplest, one command).
Document the cold-start warning in README.

### Load Shedding Feed
The brief specifies `GET /scheduled-outages` as a department-published feed to
be mocked. This is implemented: the endpoint exists and the simulator can inject
outages. However, the "treat as non-gospel" logic (outages that run late,
unexpected cancellations) is simulated by a configurable fuzz factor in the
simulator, not a real external feed.

### Geocoding / Missing Pincodes
~3% of poles have no pincode. We fall back to the ward's known pincode via a
lookup within the DT's pole set (borrow the majority pincode from sibling
poles on the same DT). No external geocoding API needed.

### Performance Targets
- Fault occurrence → ticket visible: ~3–6s (3s poll + <1s detection pass).
  Meets the <120s p95 target with large headroom.
- Ingest throughput: SQLite WAL mode + batched writes targeted at ≥500 msg/s
  on a single process. Not formally benchmarked; documented as an assumption.
- Burst tolerance: WAL mode ensures readers don't block writers. 5k messages
  in 10s = 500/s sustained, which SQLite handles comfortably at this data size.

## Assumptions Made
1. `telemetry_sim.py` was completely empty → written from scratch with
   `STALE_THRESHOLD_S = 900` (15 min × 1.0, the heartbeat interval), matching
   what `detection.py` imports from it.
2. No auth required. A hardcoded `operator` identity is used.
3. The backend and frontend run as separate Docker containers, with the frontend
   served by nginx. The backend is served by uvicorn. CORS is configured to
   allow the frontend origin.
4. `ground_truth_topology` table is never queried by any application path —
   only accessible from an offline eval script.
